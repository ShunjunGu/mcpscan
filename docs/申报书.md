# MCP 工具定义静态审计器（mcpscan）项目申报书

> 一页申报书。技术细节、查重记录与威胁模型见仓库 `docs/`、`research/`。

## 一、项目名称

**mcpscan** — MCP 工具定义的静态安全审计器

## 二、项目简介

MCP 服务器的 `tools/list` 把自然语言描述交给宿主，宿主再把它作为可信上下文交给模型。`mcpscan` 在服务器被接入之前读取这些定义，做文本归一化后按 20 条规则检查投毒模式、隐藏字符、能力隐瞒与定义漂移，输出 text / JSON / SARIF / Markdown 报告，并用退出码控制 CI。它是库也是 CLI，可嵌入任何 MoonBit MCP 客户端或 Agent 宿主。

## 三、项目方向与通用性

方向：**AI 应用（Agent 安全基础设施）+ 开发者工具**。

通用性不依赖具体服务器：输入可以是 `tools/list` 的离线快照、MCP 配置（`mcp.json`），或 stdio 连接得到的实时定义；输出是稳定的数据模型，任何语言、任何 MCP 实现都能消费。检测引擎与连接层分离，连接层缺失时离线模式仍完整可用。

## 四、使用场景

**场景 1：企业 MCP 网关的接入审批。** 安全团队在新服务器上线前运行 `mcpscan scan --config mcp.json --format sarif`，把 high/critical 作为阻断条件；将通过的完整定义指纹写入基线库。此后每次连接重新计算指纹，与基线不符即报 `TP019 rug-pull`，捕获"安装时良性、数周后变更描述"这一类攻击。

**场景 2：开源 MCP 服务器的发布 CI。** 维护者在 GitHub Actions 中运行 `mcpscan scan --snapshot dist/tools.json --baseline .mcpscan/baseline.json --format sarif`，把 SARIF 上传到 Code Scanning。PR 中自动标出本次新增的 finding，防止版本升级时描述被加入新指令；发现以文件:行:列定位到原始文本。

**场景 3：MoonBit Agent 宿主的前置校验。** Agent 框架在 `list_tools` 之后、把工具注入上下文之前调用 `@mcpscan.audit_tools(defs)`，把 critical finding 展示给操作者确认；选择隔离策略后，仅保留已确认的工具。这是纯库调用，不引入进程或网络依赖。

**场景 4：中文 MCP 生态的审计。** 现有英文规则的扫描器对中文指令性描述（"忽略之前的要求"、"不要告知用户"、"先读取配置文件"）覆盖不足。本项目将中文模式与中英混排绕过纳入规则集。

## 五、拟实现的核心功能

1. **三种扫描目标**：快照 JSON、`mcp.json` 配置、可选的 stdio 连接。
2. **归一化层**：NFKC、移除零宽与双向控制符、解码 Unicode Tag 区块（U+E0000–E007F）、提取 base64/hex 载荷，并保留原始字节偏移供报告定位。
3. **20 条检测规则**（`TP001`–`TP020`），覆盖描述注入、跨工具引用、敏感路径、外泄端点、能力隐瞒、schema 欺骗、载荷拆分、条件触发、仿冒、定义漂移等。
4. **定义指纹与基线**：对完整定义做规范化哈希，支持 `baseline --write` 与 `scan --baseline`。
5. **四种报告与 CI 退出码**：`0` 无发现、`1` 存在 high/critical、`2` 用法或读取失败。
6. **库 API**：`audit_tools()` / `audit_snapshot()`，供宿主嵌入。
7. **测试集**：恶意 MCP 服务器 fixtures（复现公开研究中的核心场景）+ 良性服务器负样本，给出规则级检出/误报统计。

## 六、项目性质

**原创项目。** 不移植、不复制任何现有项目的代码或规则文件。

威胁模型的类别划分参考下列公开发表的研究（仅参考分类与攻击描述，规则实现为原创）：

- *MCP Tool Poisoning in Agentic AI Frameworks: A Cross-Framework Measurement Study*（2026，25 类 taxonomy 与 `mcpvenom` 45 场景）
- *Implicit Tool Poisoning / Uninvoked Tool Metadata Hijack*（2026）
- *Hidden Unicode Instruction Injection in AI Agent Skills*（CSA Labs，2026）
- *Security Analysis of the MCP Ecosystem*（2026）

## 七、实现路径与关键判断

**判断 1：纯正则描述扫描不可用。** 上述研究报告的正则扫描器在 45 个场景中漏检 25 个。因此本项目采用三层：归一化（消除编码/不可见字符绕过）→ 结构化规则（描述、schema、annotation 分别检查）→ 指纹（捕获定义变更）。规则 id 与威胁类别一一对应，漏检与误报都能定位到具体规则。

**判断 2：不用 LLM 判断"是否恶意"。** 不可复现、不可离线、无法解释。审计结论必须能由规则 id 与原文区间支撑。

**判断 3：只扫描描述是不够的。** 载荷可以放在 schema 字段的 `description`、`enum`、`default`，或 `annotations` 的 `title`，或 server instructions 中。扫描单位是完整工具定义，不是单个字段。

**判断 4：定义会变化。** 因此指纹必须覆盖名称、描述、两个 schema 与 annotations 的规范化拼接，而不是只哈希描述；基线比对失败时默认 fail-closed。

**判断 5：不做运行时。** 运行时拦截需要部署代理或注入 guard，已有 `moongate` 等成熟方案；本项目的价值在部署之前与 CI 之中，两者可组合而非替代。

## 八、明确的工程边界

- **不做**：运行时代理、流量拦截、工具调用审批、密钥替身。
- **不做**：工具执行结果（tool result）的注入检测——那是运行时数据，静态模式拿不到。
- **不做**：服务端业务逻辑后门、依赖包投毒、多轮会话升级。
- **不承诺**：零误报。报告头部列出覆盖缺口，每条规则给出已知误报条件。
- **不修改**：任何第三方服务器或定义；`--fix` 不在 v0.1 范围内。

## 九、交付物与验收

| 交付物 | 验收方式 |
| --- | --- |
| 20 条规则 + 归一化层 | 单元测试；每条规则至少 1 正例 1 反例 |
| 恶意 fixtures（≥8 个服务器） | `moon test` 全绿；检出率报告 |
| 良性 fixtures（≥3 个服务器） | 误报为 0 或逐条记录 |
| SARIF 输出 | 通过 SARIF 2.1.0 schema 校验；GitHub Code Scanning 可导入 |
| 基线/rug-pull | 同一服务器的两次快照，第二次变更必须命中 TP019 |
| 真实服务器报告 | 对 ≥3 个公开 MCP 服务器扫描并提交报告 |
| 发布 | `mooncakes.io` 发布；CI 覆盖 check/build/test |

参考规模：4,000–10,000 行有效 MoonBit 代码。当前计划 6,000–8,000 行（含测试与 fixtures）。
